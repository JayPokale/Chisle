The key insight here is that the migration works as a series of small, shippable steps, not a rewrite. The main patterns are:
1. Strangler fig pattern - new service intercepts requests, monolith handles what isn't extracted yet
2. Data ownership - copy data, then gradually migrate writes
3. Ordering - pull out services that have few dependencies, leave coupled ones for later
4. Keep it shippable - each step is a production deploy

Let me think through the actual approach:

**Ordering:**
- Start with services that are depended *on* (bottom of dependency graph), not services that depend on others
- Pull out things with minimal coupling first
- Leaves monolith still functional, doesn't break existing flows

**Data ownership:**
- Strangler pattern on the data side: new service gets its own DB
- Initially, monolith writes to both old location and new service's DB (dual write)
- Migrate reads to new service
- Then migrate writes
- Then delete old data
- Need to handle consistency - reads still hit old data for a bit, then gradually switch

**Keeping it shippable:**
- Each extracted service is behind a feature flag or router
- Monolith still handles requests, just delegates to new service
- If new service breaks, switch traffic back
- No "big bang" cutover - gradual traffic shift
- Can roll back any step
