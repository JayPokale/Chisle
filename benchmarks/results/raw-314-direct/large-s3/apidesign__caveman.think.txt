Let me think through each:

**Resources:**
- `/tenants/{tenantId}/documents` - main resource
- `/tenants/{tenantId}/documents/{docId}` - single doc
- `/tenants/{tenantId}/documents/{docId}/versions` - version history
- `/tenants/{tenantId}/documents/{docId}/versions/{versionId}` - specific version

Why: tenant isolation in URL = clear separation. Version as sub-resource = natural hierarchy.

**Auth:**
- JWT token with tenant claim
- Each request must specify tenant (URL) and token validates that tenant claim
- No cross-tenant access
- API key alternative for service accounts

Why: tenant claim in token = enforced isolation at auth layer. URL tenant id = defense in depth.

**Pagination:**
- Cursor-based for consistency (offset-based breaks with concurrent inserts)
- Cursor = opaque string (base64 of last-seen ID or timestamp)
- Limit param (1-100, default 20)
Now I'm settling on how pagination returns its next-page information, and why a cursor holds up better than an offset when the data changes between requests. Then I'm moving on to versioning: the API version goes in the URL, and each document version is a numbered, immutable record that can be fetched with a query parameter.
