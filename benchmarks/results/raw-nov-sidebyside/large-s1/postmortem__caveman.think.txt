Root Cause:
Payment API degradation from an unindexed `user_id` query on a 400k-row table turns into 45s response times. Our service holds connections open waiting (60s timeout), connections pile up in WAITING state, the pool hits its 100-conn cap, and new requests throw `ConnectionPoolExhaustedException` → HTTP 503 across the board for 4 hours.

Why it wasn't caught sooner: we don't monitor Payment API's SLO, pool metrics only alert at full capacity (too late), and no circuit breaker existed.

Fallout: full outage of order processing, ~180k failed requests, ~$47k revenue loss, 23 Twitter complaints, 8 support tickets.

Digging deeper — no retry logic, no fast-fail, no queue limits meant requests just sat until timing out. No SLA with the Payment API team either, so no visibility into their

degradation.

Fix: circuit breaker went live at 15:30 UTC (5 failures or >10s latency triggers fast-fail), pool recovered within 2 minutes. Next 48 hours: Payment team adding an index on `user_id` to cut query latency from 200ms to 50ms, and we're adding alerting for p99 latency >5s routed to Slack.

TA: Deploy by 2026-11-07.

Also shrinking the connection pool timeout from 60s to 10s so calls fail fast instead of hanging, same ETA. Medium-term, backend team will add queue size limits (reject above 50) to handle surges better, targeting 2026-11-20, and engineering needs to formalize an SLA with Payment API — p99 under 500ms, 99.9% uptime, with a clear escalation path.

Longer-term items: multi-region failover for Payment API calls since we currently have no redundancy (infra, 2026-12-06), and QA load-testing the circuit breaker under realistic conditions including full Payment API outage (2026-11-13).
