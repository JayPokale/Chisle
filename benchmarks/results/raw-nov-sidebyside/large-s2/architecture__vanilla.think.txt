Let me think about the main approaches:

1. **Ordering/Sequencing:**
   - Start with the seams in the monolith - identify areas of loose coupling
   - Usually start with pieces that have few dependencies or are needed by many (domain decomposition)
   - Often start with cross-cutting concerns or bounded domains that are well-encapsulated
   - Work outward from stable foundations

2. **Data Ownership:**
   - Each service owns its own data
   - The hardest part of the migration - splitting databases
   - Need to handle the transition period where data might live in multiple places
   - Foreign key relationships become eventual consistency/events

3. **Keeping it Shippable:**
   - Use strangler fig pattern - gradually route traffic to new services
   - Feature flags to toggle between old and new implementations
   - Dual writes during transition
   - Incremental deployment and testing
   - Never remove the old code until you're sure the new service works

Key patterns and approaches:
- Strangler Fig Pattern
- Feature flags
- Adapter/wrapper patterns
- Database per service
- Eventual consistency
- Events/message queue for inter-service communication
- Contract testing
