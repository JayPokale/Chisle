# Database Connection Pooling

## The problem it solves

Opening a database connection is expensive. Each new connection typically involves:

1. A TCP handshake (and often a TLS handshake)
2. Authentication (credentials, sometimes SCRAM or similar multi-round exchanges)
3. Session setup on the server (in PostgreSQL, a whole backend process is forked; in MySQL, a thread is allocated)
4. Initial configuration (character set, timezone, search path)

That can cost anywhere from a few milliseconds to tens of milliseconds, which is often more than the query itself. Doing it for every request wastes time and hammers the database server.

## How a pool works

A connection pool is a cache of open, ready-to-use connections kept inside your application (or in a proxy in front of the database).

1. **Initialization**: The pool opens some minimum number of connections at startup (or lazily).
2. **Checkout**: When code needs the database, it asks the pool for a connection. If an idle one exists, it's handed over immediately. If not, and the pool is below its maximum size, a new connection is created. If the pool is at its maximum, the caller waits in a queue (up to a timeout).
3. **Use**: The caller runs its queries or transaction on that connection exclusively.
4. **Return**: When done, the connection goes back to the pool rather than being closed. The pool typically resets its state (rolls back any open transaction, clears session variables) so the next user gets a clean connection.
5. **Maintenance**: In the background, the pool validates connections (health checks or a ping on checkout), evicts ones that have been idle too long or lived past a maximum lifetime, and replaces broken ones.

```python
# Conceptual example
pool = ConnectionPool(min_size=5, max_size=20, timeout=30)

with pool.connection() as conn:     # checkout
    conn.execute("SELECT ...")      # use
                                    # automatic return on exit
```

## Common configuration knobs

| Setting | Purpose |
|---|---|
| Min / max size | Bounds on open connections |
| Acquire timeout | How long a caller waits when the pool is exhausted |
| Idle timeout | Close connections unused for a while |
| Max lifetime | Recycle connections periodically (avoids stale state, works with load balancers and failovers) |
| Validation query / test-on-borrow | Detect dead connections before handing them out |

## Why it helps

- **Lower latency**: Skips connection setup on the hot path. Requests pay only for the query.
- **Higher throughput**: Less CPU and network overhead on both app and database.
- **Bounded load on the database**: Databases handle a limited number of concurrent connections well (PostgreSQL in particular degrades with hundreds or thousands). A pool caps this, and excess demand queues in the app rather than overwhelming the server.
- **Resource stability**: Prevents connection storms during traffic spikes and avoids exhausting file descriptors or server memory.
- **Graceful backpressure**: When the pool is saturated, requests wait or fail fast with a clear timeout instead of causing cascading failures.
- **Centralized management**: One place to handle reconnection, health checks, and metrics.

## Pitfalls to watch for

- **Connection leaks**: Forgetting to return a connection (e.g., not closing it in an error path) slowly drains the pool until everything blocks. Use context managers or `try/finally`.
- **Pool too large**: More connections don't mean more throughput. Beyond the database's capacity to run queries in parallel (roughly tied to CPU cores and disk), they just add contention. A common starting point is a modest size (e.g., 10-20 per app instance) and then tuning. Remember that total connections = pool size × number of app instances.
- **Pool too small**: Requests queue up and latency rises.
- **Session state leakage**: Session-level settings, temp tables, or advisory locks can leak to the next borrower if the pool doesn't reset them.
- **Long transactions**: Holding a connection while waiting on slow external calls ties up pool capacity.
- **Pooler modes**: With external poolers like PgBouncer, *transaction pooling* gives the best connection reuse but breaks features that rely on session state (prepared statements in some configs, `LISTEN/NOTIFY`, session-level advisory locks).

## Where pooling lives

- **In-process libraries**: HikariCP (Java), SQLAlchemy's pool, `pgxpool` (Go), `node-postgres` Pool, etc.
- **External proxies**: PgBouncer, PgCat, ProxySQL, or managed options like RDS Proxy. These are especially useful with many app instances or serverless functions, where per-process pools would multiply connection counts.

In short: pooling trades a small amount of memory and bookkeeping for much lower latency and a database that is protected from unbounded connection demand.

Pool = set of pre-opened DB connections, reused across requests instead of opened per request.

**Mechanics:**
- App starts → pool opens N connections (min size), keeps them idle.
- Request needs DB → `acquire()` takes an idle connection. None free → open new one if under max, else block (queue) until one's released or timeout.
- Request done → `release()` returns connection to pool. Not closed.
- Pool also validates connections (ping/test query), evicts stale or broken ones, and closes extras idle past a timeout.

**Why it helps:**
- Connection setup is expensive: TCP handshake, TLS, auth, session init, and server-side process/memory per connection (Postgres forks a process per connection). Per-request open/close adds tens of ms of latency and heavy load on the DB.
- Caps concurrency: max pool size bounds connections hitting the DB, so traffic spikes queue in the app instead of exhausting the server's `max_connections`.
- Steadier latency and throughput under load; fewer connection-churn failures (ephemeral port exhaustion, TIME_WAIT buildup).

**Gotchas:**
- Size it small. Rule of thumb: roughly `cores × 2 + disk spindles` per DB, not hundreds. More connections → more contention, not more speed.
- Pool size × app instances must stay under server `max_connections`. With many instances, use an external pooler (PgBouncer, ProxySQL, RDS Proxy).
- Leaks: forgetting to release (no `finally`/context manager) → pool exhausts, requests hang. Always release in a `finally`/`with`.
- Session state (temp tables, `SET`, open transactions, advisory locks) persists on a reused connection unless the pool resets it. PgBouncer transaction mode breaks session-level features.

- Stale connections after DB restart or firewall idle-kill: enable health checks or max connection lifetime.

A **backreference** lets a regular expression match the same text that an earlier capturing group already matched. You refer to the group by its number (`\1`, `\2`, ...), so the pattern requires that part of the input to repeat exactly.

**Example: finding repeated words**

```
\b(\w+)\s+\1\b
```

- `(\w+)` captures a word into group 1.
- `\s+` matches the whitespace after it.
- `\1` matches the exact same text that group 1 captured.

Against `"this is is a test"`, it matches `is is`. It would not match `is a`, because `\1` must equal what was captured (`is`), not just any word.

Some flavors also support named groups, e.g. `(?<word>\w+)\s+\k<word>` in JavaScript or `(?P<word>\w+)\s+(?P=word)` in Python.
~~~

## REST vs GraphQL for a New API

**REST strengths**
- **Simplicity:** Familiar to nearly every developer; easy to learn, debug, and test with curl or a browser.
- **HTTP caching:** Resource URLs work naturally with CDNs, ETags, and browser caches.
- **Tooling and ecosystem:** Mature support for auth, rate limiting, logging, and monitoring, since these map cleanly to endpoints.
- **Operational predictability:** Per-endpoint cost is easy to reason about, and rate limiting is straightforward.
- **Public API friendliness:** Easy for third parties to adopt; OpenAPI gives docs and codegen.

**REST weaknesses**
- **Over-fetching/under-fetching:** Fixed response shapes can return too much or force multiple round trips.
- **Versioning:** Evolving the API often means `/v2` or careful additive changes.
- **Endpoint sprawl:** Diverse clients (web, mobile) may push you toward bespoke endpoints.

**GraphQL strengths**
- **Client-specified queries:** Clients request exactly the fields they need, often in one round trip.
- **Strongly typed schema:** Introspection, generated types, and self-documenting APIs.
- **Schema evolution:** Add fields and deprecate old ones without versioning.
- **Good for varied clients:** Frontend teams can iterate without waiting on backend changes.

**GraphQL weaknesses**
- **Caching is harder:** Typically a single POST endpoint, so HTTP caching needs persisted queries, GET support, or client-side caches.
- **Performance risks:** N+1 resolver problems (need DataLoader-style batching) and expensive nested queries.
- **Security and cost control:** Requires query depth/complexity limits, cost analysis, and timeouts to prevent abuse.
- **Operational complexity:** Error handling (often HTTP 200 with errors in the body), observability, and rate limiting are less straightforward.
- **Learning curve:** More concepts for the team (schema design, resolvers, federation).

**Recommendation**
- Choose **REST** if you're building a public or simple CRUD-style API, have a small team, rely on HTTP caching, or have few client types.
- Choose **GraphQL** if you have multiple clients with differing data needs, deeply relational data, or a frontend-heavy team that needs to iterate quickly, and you're willing to invest in the supporting infrastructure.
- For most new projects without a clear GraphQL need, start with REST. You can add a GraphQL layer later, such as a BFF, if client needs demand it.
~~~

### vanilla: 1760 answer tokens, 1760 billed, 79 lines

~~~
# Database Connection Pooling

## The problem it solves

Opening a database connection is expensive. Each new connection typically involves:

1. A TCP handshake (plus a TLS handshake if encrypted)
2. Authentication and session setup
3. Server-side allocation (in PostgreSQL, a whole process per connection; in MySQL, a thread plus buffers)

This can cost anywhere from a few milliseconds to tens of milliseconds. If your app opens a connection per request, runs a 2 ms query, and closes it, most of the time goes to setup and teardown. Databases also cap concurrent connections (e.g. PostgreSQL defaults to 100), so a traffic spike can exhaust them and cause failures.

## How a pool works

A pool is a cache of already-open connections that the application shares.

1. **Initialization**: At startup, the pool opens some minimum number of connections and keeps them idle.
2. **Checkout**: When code needs the database, it asks the pool for a connection. If an idle one exists, it's handed over immediately, with no handshake.
3. **Use**: The code runs its queries or transaction on that connection.
4. **Return**: When done, the code "closes" the connection, but that actually returns it to the pool, with state reset (rolling back open transactions, clearing session settings).
5. **Growth**: If none are idle and the pool is below its maximum size, it opens a new one.
6. **Waiting**: If the pool is at its maximum, the requester queues until a connection is returned or a timeout expires, at which point it gets an error.
7. **Maintenance**: Background logic validates connections (health checks or test queries), evicts ones that are stale or broken, and retires connections past a maximum lifetime.

```
 App threads                Pool                    Database
 ┌────────┐             ┌──────────┐
 │ req 1  │──checkout──▶│ conn A ●─┼────────────────▶│
 │ req 2  │──checkout──▶│ conn B ●─┼────────────────▶│
 │ req 3  │──(waits)    │ conn C ○ │  (idle)         │
 └────────┘             └──────────┘
```

## Why it helps

- **Lower latency**: Skipping connection setup removes a fixed cost from every request.
- **Bounded load on the database**: A max pool size caps concurrent connections, protecting the database from being overwhelmed. Excess demand queues in the app rather than crashing the DB.
- **Higher throughput**: Less CPU and memory is spent on creating and destroying connections, on both client and server.
- **Resilience**: Validation and eviction detect dead connections (after a DB restart or network blip) and replace them instead of surfacing errors.
- **Predictable resource use**: Connection count is a tunable, observable number rather than a function of traffic.

## Key configuration knobs

| Setting | Purpose |
|---|---|
| Min/max pool size | Floor of warm connections and hard ceiling |
| Acquire/checkout timeout | How long a caller waits before failing |
| Idle timeout | When to close unused connections above the minimum |
| Max lifetime | Recycle connections periodically (avoids issues with firewalls, load balancers, memory growth) |
| Validation query / keepalive | How to confirm a connection is still alive |

## Practical tips and pitfalls

- **Bigger isn't better.** A database can only do so much parallel work, bounded by its CPU cores and disk. An oversized pool causes contention. Many teams do well with surprisingly small pools (often tens, not hundreds). A common starting heuristic is roughly `(core_count × 2) + effective_spindle_count`, then tune with measurement.
- **Always return connections.** Leaks (forgetting to close, or an exception skipping the release) slowly drain the pool until everything blocks. Use `try/finally` or context managers.
- **Don't hold connections while doing slow non-DB work** (HTTP calls, heavy computation); it starves other requests.
- **Mind the multiplier.** Total connections = pool size × number of app instances. Ten instances with a pool of 20 means 200 connections to the DB.
- **External poolers** like PgBouncer or ProxySQL sit between apps and the database, multiplexing many client connections onto a few server connections. This is useful with many app instances or serverless functions. Note that transaction-level pooling breaks session-scoped features such as prepared statements, advisory locks, and `SET` variables.

## Minimal example (Python, SQLAlchemy)


~~~
Pool = set of pre-opened, reusable DB connections kept by the app. Request borrows one, runs queries, returns it. Connection is never closed between uses.

**Mechanics**
- Startup: pool opens `min` connections (TCP + TLS + auth done once).
- Borrow: idle connection available → handed out instantly. None idle and below `max` → open new one. At `max` → caller waits in queue, up to a timeout, then errors.
- Return: connection goes back to idle list. Good pools reset state first (rollback open txn, clear session vars, temp tables).
- Maintenance: health checks (validation query/ping), idle timeout to shrink toward `min`, max lifetime to recycle connections (avoids stale ones killed by firewalls/LB/DB restarts).

**Why it helps**
- Connect cost removed: new connection = TCP handshake + TLS + auth + server session setup, often 10s of ms. Query may take 1 ms. Pooling amortizes this.
- DB protected: each Postgres connection is a backend process (~MBs RAM); MySQL a thread. Unbounded app connections → memory exhaustion, context-switch thrash. `max` caps concurrency → predictable load.
- Backpressure: surge queues in the app instead of overwhelming the DB.
- Fewer ephemeral ports / TIME_WAIT sockets from connection churn.

**Gotchas**
- Sizing: bigger ≠ faster. Beyond roughly `cores*2 + spindles` active queries on the DB, throughput drops. Total = `pool_size × app instances` must stay under the DB's `max_connections`.
- Leaks: forgetting to return a connection (no `finally`/context manager) → pool exhausted → everything hangs on borrow timeout.
- Long transactions hold a connection the whole time → starve others.
- Session state leaks between borrowers if not reset.
- Many instances/serverless → per-app pools multiply; use an external pooler (PgBouncer, RDS Proxy). Transaction-mode poolers break session features (prepared statements, `SET`, advisory locks).
~~~

> Explain what a regular expression backreference is, with one short example.

### vanilla: 348 answer tokens, 348 billed, 18 lines

~~~
A **backreference** lets a regex match the same text that an earlier capturing group already matched. You refer to the group by number (`\1`, `\2`, ...), and the pattern requires that exact text to appear again.

**Example: find repeated words**

```
\b(\w+)\s+\1\b
```

- `(\w+)` captures a word into group 1.
- `\s+` matches the whitespace after it.
- `\1` must match the exact same text that group 1 captured.

Against `This is is a test`, it matches `is is`. It won't match `is a`, because `\1` demands `is` again, not just any word.

Notes:
- Some flavors also support named groups, e.g. `(?<w>\w+)\s+\k<w>` in JavaScript or `(?P<w>\w+)\s+(?P=w)` in Python.
- In replacement strings, backreferences are often written `$1` or `\1` to reuse captured text.
- Backreferences make a regex non-regular in the formal sense, and can be slow on pathological inputs because engines must backtrack.
~~~

~~~
## REST vs GraphQL for a new API

**REST strengths**
- **Simplicity and familiarity:** Widely understood, with abundant tooling and a low onboarding cost.
- **HTTP caching:** Resource URLs work naturally with CDNs, browser caches, and ETags.
- **Operational clarity:** Per-endpoint monitoring, rate limiting, and auth are straightforward.
- **Predictable load:** Each endpoint has a known cost, so performance tuning is easier.
- **File uploads, streaming, webhooks:** Handled natively over HTTP.

**REST weaknesses**
- **Over-fetching and under-fetching:** Clients get fixed payloads and often need multiple round trips.
- **Versioning pressure:** Evolving responses can lead to `/v2` or sprawling optional fields.
- **Many endpoints:** Each new client need can mean a new endpoint.

**GraphQL strengths**
- **Client-specified queries:** Clients request exactly the fields they need in one round trip, which is useful for mobile and varied frontends.
- **Strongly typed schema:** Self-documenting, introspectable, and good for codegen and typed clients.
- **Schema evolution:** Add fields and deprecate old ones without versioning.
- **Aggregation:** A good gateway layer over multiple backend services.

**GraphQL weaknesses**
- **Caching is harder:** Typically a single POST endpoint, so you need client-side normalized caches or persisted queries.
- **Performance risks:** N+1 resolver problems (mitigate with DataLoader), and expensive or deeply nested queries require depth/complexity limits.
- **Security surface:** Introspection, query abuse, and field-level authorization need deliberate handling.
- **Operational complexity:** Everything returns 200 with an errors array, so monitoring and error handling need extra work.
- **Steeper learning curve:** More concepts for both server and client teams.

**Recommendation**
- Choose **REST** if your API is public or third-party facing, resource-oriented (CRUD), cache-heavy, or your team is small and wants speed and simplicity.
- Choose **GraphQL** if you have multiple client types with differing data needs, deeply relational data, a rapidly evolving frontend, or want a unified layer over several services.
- For most new APIs without those pressures, start with REST. You can add a GraphQL layer later if client needs diverge.

# Migrating a monolith to services incrementally

The core approach is the **strangler fig**: build new capability around the monolith, route traffic to it gradually, and let the old code wither. Every step ends in a deployable state.

## 0. Prerequisites (do these first)

- **Make the monolith deployable and testable at will.** If releases are painful, fix that before extracting anything, since you'll be shipping constantly.
- **Add characterization tests** around the area you plan to carve out. They define "behavior preserved."
- **Get observability in place**: tracing, per-endpoint latency/error metrics, structured logs with correlation IDs. You can't verify a cutover without a baseline.
- **Introduce a routing seam**: an API gateway or reverse proxy in front of the monolith. This is your traffic switch for everything that follows.
- **Have a reason per extraction.** Independent scaling, a different team's ownership, a different release cadence, or a different tech need. "Microservices are better" is not a reason; you may end up keeping a well-structured modular monolith, and that's a fine outcome.

## 1. Modularize inside the monolith first

Before any network boundary exists, create the boundaries in code:

- Identify bounded contexts (use domain language, change-coupling in git history, and team structure).
- Enforce module boundaries: separate packages, public interfaces only, and architecture tests/lint rules that fail on cross-module imports.
- Replace cross-module calls with explicit interfaces, and replace cross-module joins and shared tables with calls through those interfaces.

This is the cheapest place to discover wrong boundaries. Moving a line in a modular monolith is a refactor; moving it between services is a migration.

## 2. Ordering: what to extract and when

Pick candidates by **value versus coupling**:

1. **First: a low-risk, loosely coupled, but real capability.** Notifications, PDF/report generation, search, media processing, and auth edge functions are typical. The goal is to prove the pipeline (CI/CD, deployment, observability, gateway routing, on-call) with low blast radius.
2. **Then: high-value seams** where the business benefit is clear: hot spots that need independent scaling, or areas where a team is blocked by shared releases.
3. **Last: the entangled core** (orders, billing, user/account), which everything depends on. Often the best answer here is to leave it as the remaining "core" monolith.

Rules of thumb:
- Extract **leaves of the dependency graph first** (things that depend on little, or that the monolith calls one-way).
- Extract one service at a time, to completion, before starting the next.
- Don't extract something that must change in lockstep with its neighbor; merge those boundaries instead.

## 3. Data ownership (the hard part)

Each service must eventually be the **sole owner and sole writer** of its data. Shared databases are the main thing that turns services into a distributed monolith. Do it in stages:

1. **Logical separation in the shared DB**: give the module its own schema/tables, and forbid other modules from touching them directly (enforce with DB roles).
2. **Replace cross-boundary joins** with:
   - API calls (for fresh, authoritative reads),
   - replicated read models fed by events (for hot or latency-sensitive reads), or
   - data denormalized at write time (e.g. store the customer name on the order).
3. **Split the physical database** only after nothing else reads or writes the tables directly.
4. **Migrate the data** with the expand/contract pattern:
   - **Expand**: stand up the new store. Dual-write or use CDC (change data capture) to keep it in sync with the old one.
   - **Backfill** historical data and **verify** by continuously comparing old and new.
   - **Switch reads** to the new store (behind a flag), then **switch writes** (the new service becomes the source of truth).
   - **Contract**: stop syncing, and delete the old tables after a soak period.

Consequences to accept and design for:
- **No cross-service transactions.** Use sagas (orchestrated or choreographed) with compensating actions, plus idempotency keys on every command and consumer.
- **Eventual consistency** between read models and the source of truth. Decide per use case where that's acceptable.
- **Reliable event publishing** via the transactional outbox pattern, so "write to DB" and "publish event" can't diverge.
- **Reference data and IDs**: keep IDs stable across the cutover, and have other services store foreign IDs, not copies of ownership.

## 4. Cutting over traffic safely

For each extraction, follow the same playbook:

1. **Define the contract** (API or events) and put a thin adapter/anti-corruption layer in the monolith that calls it, so the monolith's internals don't leak into the new service's model.
2. **Build the service alongside** the in-monolith code, which stays live.
3. **Shadow traffic**: mirror requests to the new service, compare responses, and discard the new service's output. Fix discrepancies.
4. **Canary by flag**: route 1%, then 10%, 50%, and 100%, by tenant, user cohort, or percentage. Watch error rate, latency, and business metrics at each step.

- **Freeze or route feature work carefully**: new features in an area being extracted should go into the new service, not the old code, or you chase a moving target.

- Extracting by technical layer (a "database service", a "validation service") instead of by business capability.
- Chatty synchronous call chains that make latency and availability worse than the monolith had.
- Shared database "just for now" that becomes permanent.
- Building the platform (service mesh, Kubernetes, event bus) far ahead of need. Add infrastructure as extractions demand it.
- Skipping the deletion step, so you end up with the monolith plus N services.

```sql
BEGIN;

ALTER TABLE users ADD COLUMN IF NOT EXISTS first_name text;
ALTER TABLE users ADD COLUMN IF NOT EXISTS last_name  text;

-- 2. Backfill, but only if full_name still exists, and only rows not yet migrated.
DO $$
BEGIN
  IF EXISTS (
    SELECT 1
    FROM information_schema.columns
    WHERE table_schema = current_schema()
      AND table_name   = 'users'
      AND column_name  = 'full_name'
  ) THEN
    UPDATE users

    WHERE full_name IS NOT NULL
      AND first_name IS NULL      -- skip rows already migrated or edited since
      AND last_name  IS NULL;
  END IF;
END
$$;

COMMIT;
```

```python
from __future__ import annotations

from dataclasses import dataclass, field
from datetime import datetime, timezone
from enum import Enum
from types import MappingProxyType


class OrderState(str, Enum):
    CREATED = "created"
    PAID = "paid"
    SHIPPED = "shipped"
    DELIVERED = "delivered"
    CANCELLED = "cancelled"
    REFUNDED = "refunded"


S = OrderState

# Single source of truth for legal transitions (read-only).
TRANSITIONS = MappingProxyType({
    S.CREATED:   frozenset({S.PAID, S.CANCELLED}),
    S.PAID:      frozenset({S.SHIPPED, S.CANCELLED, S.REFUNDED}),
    S.SHIPPED:   frozenset({S.DELIVERED}),
    S.DELIVERED: frozenset({S.REFUNDED}),
    S.CANCELLED: frozenset(),  # terminal
    S.REFUNDED:  frozenset(),  # terminal
})


class InvalidTransitionError(Exception):
    def __init__(self, current: OrderState, target: OrderState):
        self.current = current
        self.target = target
        allowed = ", ".join(s.value for s in sorted(TRANSITIONS[current], key=lambda s: s.value)) or "none (terminal state)"
        super().__init__(
            f"Illegal transition {current.value} -> {target.value}; allowed from {current.value}: {allowed}"
        )


@dataclass
class Order:
    id: str
    state: OrderState = OrderState.CREATED
    history: list[tuple[OrderState, OrderState, datetime]] = field(default_factory=list)

    def can_transition(self, target: OrderState) -> bool:
        return OrderState(target) in TRANSITIONS[self.state]

    def transition(self, target: OrderState | str) -> "Order":
        try:
            target = OrderState(target)
        except ValueError:
            raise ValueError(f"Unknown state: {target!r}") from None
        if target not in TRANSITIONS[self.state]:
            raise InvalidTransitionError(self.state, target)
        self.history.append((self.state, target, datetime.now(timezone.utc)))
        self.state = target
        return self

    def pay(self):     return self.transition(S.PAID)
    def ship(self):    return self.transition(S.SHIPPED)
    def deliver(self): return self.transition(S.DELIVERED)
    def cancel(self):  return self.transition(S.CANCELLED)
    def refund(self):  return self.transition(S.REFUNDED)

    @property
    def is_terminal(self) -> bool:
        return not TRANSITIONS[self.state]
```

## 1. Tenancy and resources

**Decision: tenant is a path prefix, not just a token claim.**

```
/v1/tenants/{tenant_id}/...
```

Reasons: URLs are self-describing and cacheable per tenant, logs and rate limits key off the path, and a mismatch between the path tenant and the token's tenant can be rejected explicitly (a guard against confused-deputy bugs). The token is still the authority; the path is a routing and consistency check.

### Resource model

```
Tenant                 /v1/tenants/{tenant}
```

| Method | Path | Purpose |
|---|---|---|
| POST | `/collections/{c}/documents` | Create (server-generated ID) |

- **Collections as a first-level noun** give a natural unit for schema, indexes, and permissions.
- **PUT with client IDs** allows idempotent imports. **POST** is for server IDs.
- **Custom verbs with `:`** (Google AIP style) for operations that aren't CRUD, instead of overloading PATCH.
- **Soft delete** by default, with `?permanent=true` requiring a higher permission. Recoverability matters more than storage cost for a document store.
- **Large binaries** go through `/content` with signed upload URLs (`POST .../content:initiateUpload`), keeping JSON endpoints small.

## 2. Auth model

**Authentication (who):**
- **OAuth 2.0 / OIDC bearer tokens (JWT)** for human users and first-party apps; short-lived (≤15 min) with refresh.
- **Client-credentials grant** for service-to-service.
- **Scoped API keys** (`/api-keys`) for simple integrations: shown once, stored hashed, tenant-bound, optional expiry and IP allowlist.

**Authorization (what):**
- **RBAC with per-collection scoping**, e.g. `documents.read`, `documents.write`, `documents.delete`, `collections.admin`, `members.admin`.
- Role binding: `(principal, role, resource scope)` where scope is tenant or a specific collection. Custom roles are tenant-defined.
- Token carries `tenant_id` and scopes; **the server re-checks role bindings from the store** for writes (or uses short TTLs) so revocation takes effect quickly.

**Isolation (the critical part):**
- Every query is forced through a tenant-scoped data-access layer. Tenant ID comes from the verified token, never from request bodies.
- Defense in depth: Postgres row-level security (`tenant_id` in every table and index prefix), or separate schemas/databases for high-tier tenants.
- **Return 404, not 403, for resources in other tenants** to avoid existence leaks. Use 403 only when the caller is in the tenant but lacks permission.
- Per-tenant encryption keys (envelope encryption) as an option for regulated customers.
- Per-tenant rate limits and quotas, so a noisy tenant cannot starve others.

## 3. Pagination

**Decision: opaque cursor-based pagination.**

```
GET /v1/tenants/t1/collections/c/documents?page_size=50&page_token=eyJ...
```
```json
{
  "items": [ ... ],
  "next_page_token": "eyJ...",
  "has_more": true
}
```

Why not offset: offsets get slow on deep pages and give duplicates or skips under concurrent writes. Cursors encode the last sort key (e.g. `(updated_at, id)`) so pages are stable and use an index seek.

Details:
- `page_size` default 50, max 200.
- Tokens are opaque, signed, and bound to the tenant plus the filter/sort so they can't be replayed across queries or tenants. They expire (e.g. 24h).
- Sorting: `order_by=updated_at desc`, restricted to indexed fields with `id` as a tiebreaker.
- Filtering: simple `?filter=labels.status=draft` for GET, with a richer syntax on `:search`.
- No total count by default (expensive); `?include_total=estimate` is opt-in.
- Link headers (RFC 8288) are optionally included for generic clients.

## 4. Versioning

Two distinct concerns:

**API versioning: major version in the URL (`/v1/`).** It's visible, easy to route, cache, and document. Only breaking changes bump it. Additive changes (new fields, endpoints, optional params, enum values) are non-breaking, and clients must ignore unknown fields. Deprecation uses `Deprecation` and `Sunset` headers (RFC 8594) plus a minimum 12-month window. Optional date-based opt-in for minor behavior (`API-Version: 2026-11-19`) can be added later without a `/v2`.

**Document versioning: revisions and optimistic concurrency.**
- Each write increments `revision`, and `ETag` carries it.
- Updates require `If-Match: "7"`. Mismatch returns `412 Precondition Failed`. A missing header returns `428 Precondition Required` (configurable per collection; lenient mode allows last-write-wins).
- Revisions are immutable and retained per a retention policy. `GET .../documents/{id}?revision=5` reads history.
- `If-None-Match: *` on PUT means create-only.

**Idempotency:** POST accepts an `Idempotency-Key` header, stored per tenant for 24h. Replays return the original response.

# Migrating a monolith to services incrementally

The approach is the strangler fig: grow new services around the monolith, route traffic to them one slice at a time, and delete the old code as it becomes dead. At every step the system is in production and working.

## 0. Prepare before extracting anything

- **Make the monolith modular first.** Enforce module boundaries inside it (packages, dependency-rule linting, no cross-module table access). A modular monolith is often the right stopping point, and if not, it makes extraction mostly mechanical.
- **Build the safety net.** Characterization tests on critical flows, CI that deploys on every merge, observability (tracing, structured logs, per-endpoint metrics), and feature flags. Without these, you can't tell whether an extraction worked.
- **Establish a seam for routing.** Put a facade, API gateway, or reverse proxy in front so traffic can be shifted per route without clients knowing.
- **Define the goal.** "Independent deploys for team X" or "scale the image pipeline separately" are real reasons. "Microservices are modern" is not. Each extraction should have a concrete payoff.

## 1. Ordering: what to extract and when

Pick candidates by value and risk, and start with a low-risk one to build the platform muscle (CI/CD templates, service discovery, auth propagation, tracing).

| Good early candidates | Bad early candidates |
|---|---|
| Edge/leaf capabilities with few inbound dependencies (notifications, search, file processing, PDF generation) | The core domain entangled with everything (orders, accounts) |
| Components with distinct scaling or runtime needs | Anything sharing many tables with other modules |
| Areas with high change rate and a team that wants autonomy | Low-churn code that works fine |
| Stateless or lightly stateful logic | Components needing distributed transactions across many others |

Rough sequence:
1. **Pilot:** one leaf service, to prove the pipeline and operational model.
2. **Edge-in:** peel off capabilities along the dependency graph from the leaves toward the core.
3. **Core last:** by then, the core is a smaller monolith with clear interfaces, and you may decide it can stay as is.

Re-prioritize after each extraction based on what you learned.

## 2. Extracting a single service: the repeatable loop

1. **Define the contract** (API or events) from the module's existing public surface. Have the monolith call it through an interface it already uses internally.
2. **Implement the interface remotely** behind that seam, while the in-process implementation stays.
3. **Shadow/dark launch:** send mirrored traffic to the new service, compare responses, and don't use its result yet.
4. **Canary:** flag-based rollout (1% → 10% → 100%), with instant rollback by flipping the flag.
5. **Remove the old code** only after a soak period. Deleting it is what makes the extraction real; otherwise you end up with two implementations to maintain.

## 3. Data ownership

Data is the hardest part. Rule: **each table has exactly one owning service, and others access it only through that service's API or events.**

Phased approach for moving data:

1. **Shared database, owned logically.** The new service reads and writes its tables in the monolith's DB, and the monolith stops touching them directly (enforce with a separate DB user/schema and permissions).
2. **Break cross-boundary joins and foreign keys.** Replace joins with API calls or locally replicated read models. Replace FKs with ID references and eventual consistency.
3. **Separate the schema, then the database.** Move to a dedicated schema, then a dedicated instance, once access is exclusively through the service.
4. **Migrate data with dual writes carefully, or better, CDC.** Prefer change data capture (e.g. Debezium) or the outbox pattern over naive dual writes, which can diverge. Sequence: backfill → sync via CDC → verify with reconciliation jobs → switch reads → switch writes → stop sync.
5. **Handle transactions.** Where an ACID transaction spanned the new boundary, redesign it as a saga or as idempotent steps with compensation. If that's too hard, it's a sign the boundary is in the wrong place; move it.

Other data rules:
- Events carry facts others need (`OrderPlaced`), so consumers keep their own read models instead of querying synchronously on every request.
- Reporting and analytics read from a warehouse fed by events or CDC, not by joining across service databases.
- Make every consumer idempotent, since delivery will be at-least-once.

## 4. Keeping it shippable throughout

- **Trunk-based development, small PRs, always deployable main.** The migration is a stream of ordinary releases, not a long-lived branch.
- **Expand/contract (parallel change) for every breaking change:** add the new path, migrate callers, remove the old path as separate releases.
- **Feature flags for routing and behavior.** Every cutover is reversible without a deploy.
- **Backward-compatible contracts.** Use consumer-driven contract tests so a service can't silently break its callers, and version APIs and events.
- **Time-box the in-between state.** Each extraction has an explicit definition of done, including deletion of old code and tables. A half-migrated state left indefinitely is worse than either endpoint.
- **Operational readiness gate per service:** dashboards, alerts, SLOs, runbooks, on-call owner, and timeouts/retries/circuit breakers on calls to it. Network calls fail in ways in-process calls don't.
- **Keep feature work flowing.** Reserve a steady fraction of capacity for migration (say 20–30%) rather than freezing features, and prefer building new features in the new service when they touch a module you're about to extract anyway.

## 5. Common failure modes

- **Distributed monolith:** services that must deploy together or share a DB. Prevent it with data ownership and contract tests.
- **Wrong boundaries:** cut along business capabilities (bounded contexts), not technical layers. If two services change together constantly or chatter heavily, merge them.
- **Too many services too early:** the operational cost is real. Extract only when the payoff justifies it, and stop when the pain is solved.
- **No deletion:** the monolith never shrinks, and you've just added complexity.

## Summary

Make the monolith modular, put a routing seam in front, extract leaf-first with a repeatable shadow → canary → delete loop, give every table a single owner and move data via CDC/outbox with reconciliation, and ship every step behind flags so rollback is always one flip away. Measure each extraction against the concrete problem it was meant to solve, and stop when those problems are solved.

- One service, one owner per table. Others get access only through the service's API or events, never by reading its DB.

- Main stays releasable: no long-lived migration branch. Everything lands behind flags, defaulting to the old path.
